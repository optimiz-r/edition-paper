# edition-paper performance on Linux

This report records experiments from November 23. The bundled Playwright size and timing measurements below describe those builds. The 1.1.0 candidate uses the full Playwright Core 1.65.1 npm dependency and a different print readiness wait.

The published npm 1.0.0 tarball and the tarball packed from main at `e97ada55fdcec2f1b9412bef6e6301f861be6399` had identical SHA-512 digests. Their dependency resolutions differed. Published used Playwright Core 1.65.1 and main used its lockfile's 1.64.1. Default renders used the same installed Google Chrome 157.0.8103.38.

## Changes by measured impact

1. **Opt-in headless shell installation.** `EDITION_PAPER_INSTALL_CHROMIUM=1` uses the bundled Playwright installer for the shell and FFmpeg if launch fails. Installed Chrome still rendered with zero download bytes. The mirror run transferred 134,324,508 B, down 60.9% from the published full installer and 59.1% from main. The first archive fell from 199.3 MiB / 191.1 MiB to 125.7 MiB. Compatibility class is opt-in onboarding. Size and byte progress depend on the mirror supplying a response with a content length. CDN delays were outside this measurement.
2. **Trimmed Playwright distribution.** Cold archive payload fell by about 56% and external runtime dependencies went from one to zero. The staged runtime contains unmodified upstream files, the matching installer, and the notices. The package and installed scheduler copy require no setup hook. Compatibility class is packaging and a runtime pin to the version observed for a fresh published install. Users who pinned main's 1.64.1 and only cached its managed browser need the matching 1.65.1 browser or system Chrome when moving to this package. Existing scheduled copies retain their installed driver. The release file allowlist and browser fixtures need verification on every driver upgrade.
3. **Image completion events.** Waiting on load/error and keeping a 250 ms fallback retained the 20-second deadline and image warnings. In the revision comparison, the post-image median was 178.3 ms for 1.0.0, 183.4 ms for main, 51.5 ms for the 50 ms polling experiment and 51.6 ms for the event-driven wait. The two experiments had overlapping warm spreads. The event-driven version avoids the more frequent protocol polling. Compatibility class is an internal timing change. The fixture checks included lazy images in a shadow root, a broken image, and an empty edition.
4. **Configured system Chromium.** `EDITION_PAPER_CHROMIUM_EXECUTABLE` takes an absolute trusted executable path, launches with a temporary profile and the sandbox enabled, and falls back to managed Chromium if launch fails. Auto still tries Chrome first. The executable-path smoke printed `Configured executable launched with sandbox enabled.` using the installed Chromium-based Chrome binary. Compatibility class is opt-in browser selection.

The CLI already imported the driver lazily, opened one isolated context, waited for the ready marker and blocked the known analytics host. Those paths were measured with their existing behavior. Arbitrary app resources and concurrent browser work before input validation were left outside the optimized path.

## Targets that remain open

- **T1 warm time.** The final median was 6.6% below published and 6.4% below main. The measured 300 ms fixture response pipeline alone took 1,750.8 ms median (1,730.2–1,777.6 ms), above the 1,258.6 ms whole-run budget. Eliminating CLI and browser startup could not reach that budget on this workload. The owner needs to decide whether the app can overlap or reduce required requests, or revise the target for this network fixture.
- **T2 cold npx time.** The final archive payload fell 56.5% vs published and 55.6% vs main. Install time fell 16.4% and 27.8%, respectively. A separate rotating control used a 298 B version-only tarball and measured 538.1 ms median (396.4–680.9 ms), above both the release comparison’s 342.0 ms and 395.9 ms budgets. The owner needs to decide whether to retain the pasted cold npx command and grade payload independently, or use a distribution path that removes npm startup from the first run.

## Output, compatibility and gates

- The complete parity run matched every page's size and pixel hash at 96 DPI and the hash of layout-preserving extracted text. The five checks were daily 2 pages, large 30, mixed 1, empty 1 and explicit managed Chromium daily 2. Every page was 595.92 × 842.88 pt A4.
- The first single-origin stress run dropped different subsets of large-fixture images in the baselines and candidate and produced mismatched rasters. The separate complete-fixture replay kept all 300 unique images and each 300 ms response, spread them across four loopback ports, and confirmed zero large-edition image warnings. The original single-origin timing and memory data were kept. The original fixture remained the T1 workload.
- The packed CLI comparison printed `Compared 14 invocations across published, main and final: exit codes and both streams identical.` The 45 fixture renders also matched normalized logs and status, and successful printing cases submitted the saved path and literal named-printer arguments to fake `lpr`. Empty editions saved a PDF, exited 1, and made no submission. The mock scheduler copied a packed driver and its license, resolved 1.65.1 and printed `1.0.0`. The source-checkout scheduling regression found at the first gate was fixed by preserving its installed driver in the copied runner.
- Node 20.20.2, 22.23.3, 24.13.0 and 26.13.0 each printed `tests 57`, `pass 57`, `fail 0`. Syntax checks, the prepack build, the 48-entry archive and bin mode, and packed help/version import traces passed. The repository returned `Missing script: "lint"` and `Missing script: "build"`. The publish-only live-link check was skipped. No real schedule or print queue was used. Native macOS launchd, native Windows Task Scheduler, and physical printing remain unverified.

### Playwright bundle and release compatibility

Keep the trimmed bundle. The pinned 1.65.1 release also resolved in the fresh
published 1.0.0 comparison. Compared with the published package and its
dependency, the round-two archive transfer saves about 1.83 MB (56%) and the
installed dependency count drops from one to zero. The bundle pins runtime,
installer and browser metadata together and avoids an install hook on the
pasted command. Retaining an ordinary dependency at the same exact version
would still select the same browser revision.

The upstream Playwright Core 1.65.1 archive has 116 regular files. The bundle
copies 35 of them byte for byte using the allowlist in
`scripts/stage-playwright.mjs`. It retains the package and browser manifests,
CJS/ESM entry points, installer CLI and platform scripts, bootstrap, core,
registry and utility bundles, the browser downloader, Chromium icon,
`xdg-open` and the accompanying license material. The 81 omitted files are
the upstream README, `index.d.ts` and `types/`, the interactive CLI daemon,
dashboard and MCP entry points, the Electron loader, all of `lib/tools/`
and `lib/vite/` (CLI tooling, skills, dashboard, report, recorder and trace
viewer), and the WebP screenshot encoder and its sidecar license. The bundle
contains no browser binaries.

Apache 2.0 section 4 requires passing on the license, marking modified files
and retaining applicable attribution and NOTICE material. Every retained
upstream file is unmodified. The packaged README identifies the reduced
distribution. The tarball carries `LICENSE`, `NOTICE` (Microsoft and
Puppeteer attribution), `ThirdPartyNotices.txt`, and the upstream
`lib/serverRegistry.js.LICENSE` and `lib/utilsBundle.js.LICENSE` sidecars
under `vendor/playwright-core/`. The scheduled runner copies that directory.
The first-party code continues to ship with its BSD-3-Clause license.
[Apache License 2.0, section 4](https://www.apache.org/licenses/LICENSE-2.0#redistribution)

To upgrade the driver, update the exact `playwright-core` dev dependency and
lockfile together with `npm install --save-dev --save-exact playwright-core@<version>`,
then install from the lock with `npm ci`. Check the upstream file layout
and notice sidecars against the allowlist. Run `npm pack`, unpack the tarball
in a temporary directory and run
`node scripts/stage-playwright.mjs --check <unpacked-package-directory>`
from the source checkout. Prepack validates the pin, both lockfile entries,
the installed upstream manifest, exact staged file list, contents and
license sidecars. The same check can verify the extracted package.
Run the supported Node checks and packed fixture parity, installed Chrome,
matching managed Chromium, opt-in managed download and scheduler-copy
smokes before shipping a new pin. Check the upstream browser revisions
against the retiring release when writing upgrade notes.

The published 1.0.0 tarball requested `^1.64.1`. If a user already has the
1.65.1 managed shell (revision 1255), the new package reuses it. Auto still
prefers working system Chrome. A reader with only the 1.64.1 shell (revision
1248) and no working system Chrome must get the matching shell. The default
failure keeps the one-command install hint and does not start a download.
`EDITION_PAPER_INSTALL_CHROMIUM=1` selects the smaller opt-in download.
Existing scheduled macOS copies still use their original driver until they
are reinstalled. A Linux recipe pinned to 1.0.0 keeps asking for that version.

Recommend a minor release with the managed-cache requirement in the
upgrade notes. Chrome users and those already on revision 1255 get a
patch-compatible change. A silent patch can interrupt an existing
Chromium-only invocation whose only cached shell is revision 1248.

### Where the warm run can save time

The fixture's HTML discovers its feed through an inline script. The feed
response contains the story markup and image URLs. Under screen media the
print columns are hidden and their lazy images wait until the CLI checks
the ready marker, enables print media and marks visible pictures eager.
The single loopback HTTP/1.1 origin receives six image requests concurrently,
then six more as connections become available. The fixture has no external
font, stylesheet, script or favicon request. The CSS uses a local font and the
favicon is an inline data URL.

Round two checks the same root marker in the browser on animation frames.
The original Playwright selector still checks visibility under the same
90-second budget and supplies the original fallback if the faster probe
fails. The navigation condition, print media switch, image readiness and
timeout, story count, and Chrome's A4 PDF path remain in their original order.
Playwright 1.65.1's selector-only wait backs off through 20, 50, 100, 100
and then 500 ms between checks. The feed often completes just after the
last 100 ms interval, leaving the lazy images idle until the next probe.

The CLI validates setup and output first. The first request is Chromium
navigation, so it requires a launched browser, a context with service
workers blocked and analytics routing in place, and a page. In three separate
runs instrumented on a scratch copy, argument and setup parsing took
0.842–0.982 ms and output directory creation took 0.027–0.037 ms. Driver
import took 159–183 ms and Chrome launch took 178–209 ms. There's under
1.1 ms of configuration work to overlap. An independent Node request would
duplicate navigation or take over response handling from Chromium.
Overlapping feed discovery, inferring image URLs early or multiplexing the
image waves calls for a change to the app or the fixture's transport.

The table shows the median-by-PDF-time run from each round. All timestamps
are elapsed milliseconds from CLI spawn. Each image wave groups six
independent requests. The harness records the individual paths and spans.

| Request or milestone | Round 1, sample 7 | Round 2, sample 2 |
| --- | ---: | ---: |
| `/paper` | 533.4–834.3 | 600.1–900.7 |
| `/stories/daily` | 854.5–1,155.2 | 926.8–1,227.7 |
| `/image/1`–`/image/6` | 1,669.8–1,970.8 | 1,273.6–1,578.1 |

The fixed critical path is 300 ms for HTML + 300 ms for the feed +
2 × 300 ms for the image waves = 1,200 ms on the single HTTP/1.1 origin.
With the candidate's 600.1 ms median startup, the theoretical floor is
1,800.1 ms before rendering and writing the PDF. The measured median is
128.6 ms above it. The fastest observed startup, 457.9 ms, still puts
that floor at 1,657.9 ms. One fully concurrent image wave would leave a
1,500.1 ms floor at median startup. For a 1,259 ms budget on the current
path, startup and all client work would together get only 59 ms. The owner
can revise the target for the fixed fixture or authorize changes to how the
app delivers the document, feed and images.

### Output and memory verification

Five complete 300-story renders per build produced the peak PSS numbers.
Each image response took the same 300 ms delay. The four-origin parity
fixture allowed all 300 images to complete within the usual 20-second
image deadline. Candidate median PSS was 7.4 MiB above round one with
overlapping ranges and 2.7 MiB below the published baseline.

All 100 scored parity PDFs matched on page count, page size, layout-preserving
extracted text and 96 DPI raster hashes. The five profiles had 2 daily,
30 large, 1 mixed, 1 empty, and 2 managed-Chromium daily pages. File byte
counts matched within each profile. Round one and two binary hashes matched
after normalizing creation and modification timestamps. The mixed fixture
held the successful shadow-DOM image for about 1,201 ms and served the
broken image as a 404. Every run waited for the slow response before writing
and warned only about the 404. Fixture logs and exit statuses matched.
The fake `lpr` recorded the exact named-printer arguments and written path.
The empty edition saved its PDF, exited 1 and made no submission.
A separate print-font fixture held a local font response for 1,200 ms.
All four builds wrote after the response, embedded DejaVuSansMono-Bold
and matched the raster.

The packed CLI comparison printed `Compared 14 invocations across published,
main, round 1 and round 2: exit codes and both streams identical.` The
individual runs covered info flags, parser failures and the Linux schedule
instructions. The cache smoke also checked the default PDF directory and
daily filename with a temporary home. The mocked scheduler tests and runner
copy verified schedule locations and preserved every bundled notice. The
old-cache smoke successfully rendered revision 1248 with the old driver,
revision 1255 with the new driver and system Chrome with the old cache.
Explicit Chromium with just revision 1248 exited 1 with the pinned install
hint and did not initiate a download.

Node 20.20.2, 22.23.3, 24.13.0 and 26.13.0 each reported `tests 58`,
`pass 58`, `fail 0`. `npm run lint` and `npm run build` each reported
`Missing script` on all four versions. JavaScript syntax checks, `npm pack`
with prepack verification, the 48-entry archive, and the extracted bundle
check passed on all four versions. Packed help and version did not load the
driver. Negative checks rejected an altered license sidecar with `Bundled
Playwright differs from 1.65.1` and a 1.64.1 install with `Installed
Playwright Core must match the declared pin`. The live-link prepublish check,
native launchd, Windows Task Scheduler and physical printing were skipped.

Three rotating browser-onboarding samples per build used the 300 ms loopback
archive mirror. Both original builds ran the manual Chromium installer.
The round-one and round-two builds rendered through the opt-in headless
shell download. All installed-Chrome cases rendered with zero transferred
browser bytes, and the default missing-browser cases transferred zero bytes.
Round two showed `0% of 125.7 MiB` as the shell transfer started. The
first onboarding attempt hit Chrome's Unix socket path limit in the fixture
harness and fell back to the managed download. The shortened scratch prefix
let the test exercise the installed Chrome path.
